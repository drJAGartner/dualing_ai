# Lucy Side-by-Side Testing Notes

## What Dualing AI Expects

Dualing AI currently expects each side to expose a simple HTTP prompt endpoint:

```http
POST /prompt
```

Request:

```json
{
  "prompt": "your prompt here"
}
```

Response:

```json
{
  "text": "agent response here"
}
```

The app expects to reach the two agents at:

- Left: `http://localhost:8101/prompt`
- Right: `http://localhost:8102/prompt`

## What Is Currently Running

Docker shows both Lucy comparison containers running and healthy:

- `lucy-cmp-v1.3.1`
  - Image: `lucyacr.azurecr.io/lucy:v1.3.1`
  - Port mapping: `8101 -> 8000`
  - Health endpoint: `http://localhost:8101/health`

- `lucy-cmp-v1.2.0`
  - Image: `lucyacr.azurecr.io/lucy:v1.2.0`
  - Port mapping: `8102 -> 8000`
  - Health endpoint: `http://localhost:8102/health`

Both `/health` endpoints return `200 OK` with:

```json
{
  "status": "ok",
  "agent": "pscm_workflow"
}
```

## Current Problem

Lucy is running, but Dualing AI does not yet know how to send prompts to it.

The expected Dualing AI endpoint, `/prompt`, has not been confirmed on the Lucy containers. The usual FastAPI docs endpoint `/docs` returns `404`, so the available Lucy API surface is not discoverable from OpenAPI docs at that path.

The immediate blocker is identifying Lucy's actual prompt/chat/run endpoint and request/response shape.

## Likely Fix Options

Option 1: Add a small adapter layer per side.

The adapter would expose Dualing AI's simple `POST /prompt` contract and translate requests to Lucy's native API.

Option 2: Make Dualing AI support Lucy's native API directly.

This is faster if Lucy has a stable prompt endpoint, but less general for future agent comparisons.

Option 3: Add configurable agent endpoint contracts.

This would let each side define its prompt path and request/response mapping later, but is more complexity than the first version needs.

## Next Needed Information

To proceed with real testing, we need Lucy's prompt invocation details:

- HTTP path
- HTTP method
- Request JSON shape
- Response JSON shape
- Whether session/user IDs are required
- Whether the endpoint is synchronous or streaming

Once that is known, Dualing AI can either call Lucy directly or use a thin adapter that presents the standard `/prompt` interface.

# Notes from Claude

Investigated 2026-09-24 by reading Lucy's server source and then **actually
booting both images and round-tripping prompts**. Everything below is verified,
not inferred.

## Answering "Next Needed Information"

| Question | Answer |
|---|---|
| HTTP path | `/` — the **root path**, not `/prompt` |
| HTTP method | `POST` |
| Request shape | A2A **JSON-RPC 2.0**, method `message/send` |
| Response shape | JSON-RPC envelope; answer text in `result.artifacts[]` **or** `result.status.message` |
| Session/user IDs | `contextId` (session) required for multi-turn; `userId` optional |
| Sync or streaming | **Synchronous.** A separate SSE stream exists at `/progress/{session_id}` but is not needed |

`/docs` 404s because Lucy is **not FastAPI**. It is a Starlette app generated by
Google ADK's `to_a2a()`, which publishes no OpenAPI document. The agent card is
at `/.well-known/agent-card.json`; the client-side reference implementation is
`pscm_agents_adk/chainlit_app.py` (~line 960) in the Lucy repo.

Full protocol details, env vars and gotchas: `~/lucy-comparison-harness.md`.

## Recommendation: Option 1, as a wrapper image per side

Option 1 is right, and not only for generality. **Option 2 cannot work as
written**: a single A2A turn is not a pure `prompt -> text` call (see
"input-required" below), so Dualing AI would need that state machine internally
regardless. Option 3 is premature — a configurable path/mapping still would not
express the three-shape response or the HITL turn.

Implement the adapter as a **wrapper Dockerfile per side**, so
`DockerAgentManager` keeps working unchanged: it already builds `left/` and
`right/` and runs the result. I have created and verified these:

```
left/Dockerfile   FROM lucyacr.azurecr.io/lucy:v1.3.1  + adapter
right/Dockerfile  FROM lucyacr.azurecr.io/lucy:v1.2.0  + adapter
{left,right}/start.sh    boots Lucy on :8000, waits for health, execs adapter on $PORT
{left,right}/adapter.py  A2A <-> /prompt translation (stdlib only, no pip installs)
```

The adapter honours `$PORT`, which is what `DockerAgentManager` injects, so the
default `LEFT_AGENT_PORT=8101` / `RIGHT_AGENT_PORT=8102` work as-is.

**Verified working:** both images build, both report healthy, and
`POST localhost:8101/prompt` and `localhost:8102/prompt` each return
`{"text": "..."}` from the respective Lucy version.

> Do **not** set `LEFT_AGENT_CONTAINER_PORT=8000` as `.env.example` currently
> suggests. That advice assumes Dualing AI talks to Lucy's port directly, which
> cannot work — there is no `/prompt` there. With the wrapper, the adapter is
> the thing listening on the container port. That comment should be corrected.

## Four blockers in Dualing AI itself

The notes list Lucy's API as "the immediate blocker." It is the most visible
one, but three others will bite immediately after it is cleared.

### 1. `promptTimeoutMs` is hardcoded to 30s — too short (highest priority)

`server/src/config.ts:36` sets `promptTimeoutMs: 30_000`, and it reads from no
env var. **Measured Lucy turns: 20.2s and 25.3s for a deliberately brief
prompt.** Both already sit inside the 30s budget with only seconds to spare;
realistic multi-agent turns run 30–120s. Nearly every real comparison would
abort and be reported as `"<side> agent timed out after 30s"` — a Lucy problem
that is not a Lucy problem.

```ts
promptTimeoutMs: Number.parseInt(process.env.PROMPT_TIMEOUT_MS ?? '180000', 10),
```

Suggest defaulting to 180s and adding `PROMPT_TIMEOUT_MS` to `.env.example`.

### 2. `DockerAgentManager` cannot inject environment — Lucy cannot boot without it

`server/src/docker.ts:75-86` runs:

```
docker run -d --rm --name <n> -p <p>:<cp> -e PORT=<cp> <image>
```

`PORT` is the **only** variable passed. Lucy needs Azure OpenAI, Cosmos and
Blob Storage credentials or it cannot serve a single prompt. There is currently
no way to supply them, and baking secrets into the image is not acceptable.

Add an optional per-side env file:

```ts
// config.ts
envFile: process.env[`${side.toUpperCase()}_AGENT_ENV_FILE`] ?? process.env.AGENT_ENV_FILE

// docker.ts, in startSide
...(config.envFile ? ['--env-file', config.envFile] : []),
```

Then `AGENT_ENV_FILE=./lucy.env` covers both sides. This is the single change
that makes the whole thing runnable unattended.

**Gotcha, learned the hard way:** `--env-file` does **not** strip surrounding
quotes or trailing `# comments` the way Compose does, and it **overrides the
image's own `ENV`**. Lucy's `.env` has 12 quoted values, which produced a
mangled endpoint (`/%22https:/lucy-dev.openai.azure.com%22/`) and five LiteLLM
retries before failing. Sanitize first:

```bash
sed -E -e 's/^([A-Z_]+)="([^"]*)".*$/\1=\2/' \
       -e 's/^([A-Z_]+)=([^"#]*[^"# ]) +#.*$/\1=\2/' .env > lucy.env
```

The same override behaviour also re-enabled SSL from a stale `ADK_SSL_CERTFILE`
and crashed the container; `start.sh` now forces those off at runtime, where
nothing can override it.

### 3. Startup race — `startAll()` returns before agents are ready

`main()` awaits `dockerManager.startAll()` and immediately listens. `docker run
-d` returns as soon as the container is *created*, but **Lucy takes ~40–60s** to
build its agent graph. Prompts sent in that window fail with a connection error
that looks like a broken agent.

`start.sh` already polls Lucy's own `/health` before exposing the adapter, so
the container is honest about readiness. Have `startSide` poll the side's
`/health` (with a ~120s budget) before resolving, and surface a "starting"
state via `/api/status` so the UI can disable the prompt box until both sides
are up.

### 4. `input-required` — a correct response that violates the `{text}` contract

Lucy is a human-in-the-loop agent. Its `ask_human` tool can suspend a turn to
ask a clarifying question: `status.state` becomes `input-required`, there are
**no artifacts**, and the question arrives in a `data` part rather than a text
part.

**This is a live difference between the two versions under test.** Given an
identical prompt and context:

- **v1.3.1** answered directly (`completed`)
- **v1.2.0** returned `input-required`, asking to confirm the institution

A harness that treats this as an empty answer would report "v1.2.0 returned
nothing," which is wrong, and would misrepresent the very behaviour change the
demo exists to show. Note `sendPrompt` throws unless `body.text` is a string, so
an unhandled `input-required` surfaces as a hard error.

The adapter returns the question as `text` plus `state` and `needs_input`, so
Dualing AI works unmodified today. To show these well, consider having the UI
badge a `needs_input: true` response as "agent asked a clarifying question" and
offer a reply box — replying on the same `session` continues the turn
(verified: a follow-up produced the substantive answer).

## Suggested order

1. **Timeout to 180s** — one line, unblocks everything else.
2. **`--env-file` support** — makes unattended runs possible.
3. Use the wrapper Dockerfiles (already in `left/` and `right/`).
4. Health-gated startup.
5. `needs_input` UI affordance — polish, not a blocker.

Steps 1–3 are enough for a working demo.

## Fairness notes

- Both sides share one Cosmos database; the adapter namespaces sessions per
  side (`SIDE` env var). Keep that.
- Lucy's session service is **in-memory**, so restarting a container resets
  conversational state — usually what you want between trials.
- Pass `context` (institution, state, role, population) to avoid burning turns
  on clarification. Use an exact IPEDS institution name ("Riverside City
  College", not "Riverside Community College") or Lucy spends a turn
  disambiguating.
- Responses are non-deterministic. For a demo, prefer a few prompts with clear
  behavioural differences over a large sample.
